# AstroScope v0.2.0 — Phase 0 Research Baseline Freeze

## Baseline status

AstroScope v0.2.0 is the documented Phase 0 research baseline. It freezes the capability,
architecture, limitation, and validation record that future research phases must use as their
comparison point.

- Version: `0.2.0`
- Research phase: Phase 0 — Feature Freeze & Research Baseline
- Freeze mission: Mission 20 — v0.2.0 Research Baseline Freeze
- Capability snapshot: `main` at `bc1048df3b0ecd471c0fcc788f9c7cf80aff53c3`
- Capability snapshot pull request: PR #9, Architecture & Limitations Map
- Freeze date: 2026-08-03
- Python requirement: Python 3.12 or later
- CI reference environment: Python 3.12
- Validation baseline: 702 collected tests

The Git commit that first contains this document and the `0.2.0` project metadata is the freeze
commit. A Git tag, hosted release, package publication, or deployment is not created by Mission 20.

**Readiness classification:** research-capable educational prototype. v0.2.0 is a baseline for
controlled architecture and validation work; it is not validated research software and must not
be described as publication-grade, operational, autonomous, or suitable for safety-critical
observatory control.

## Supported v0.2.0 scientific workflows

“Supported” means that the workflow is present in the v0.2.0 application or reusable modules and
is covered by the current software test strategy. It does not mean that every result has been
validated against authoritative scientific references.

### Reusable non-UI surface

The reusable baseline includes validated dataclasses and functions for observer/time conversion,
coordinate and visibility calculations, Solar System geometry, telescope/imaging calculations,
light-curve processing and searches, transit prediction/visibility/ranking, observation records,
serializers, reports, and Plotly figure builders. The package does not yet declare a stable public
API: `src/astroscope/__init__.py` remains an empty package marker, so direct module imports are
internal interfaces subject to future versioned refactoring.

## Frozen external data and dependency boundary

| Dependency | v0.2.0 usage | Reproducibility limitation |
|---|---|---|
| ESA Gaia Archive | Synchronous ADQL/TAP query of `gaiadr3.gaia_source` | Query is retained, but retrieval time, response snapshot, and archive state are not |
| NASA Exoplanet Archive | Synchronous ADQL/TAP query of `pscomppars` | Query is retained, but retrieval time, response snapshot, and archive state are not |
| Open-Meteo | Synchronous hourly forecast request | Forecast model/run/version and response snapshot are not retained |
| Astropy built-in ephemeris | Solar System, planner, and transit geometry | Reference-data identity is not recorded in result products |
| Astropy IERS data | Time-dependent coordinate transforms | Freshness/version policy is not explicit in application output |
| System timezone database | Local/UTC conversion through `zoneinfo` | tzdata version is not recorded |
| User-supplied photometry/logs | In-memory upload | Source checksum, mandatory instrument metadata, and durable storage are absent |
| Python dependencies | Minimum version ranges in `pyproject.toml` | No lockfile or exact research environment snapshot exists |

Remote requests are synchronous and timeout-bounded. v0.2.0 provides no application-level retry,
cache, rate-limit policy, circuit breaker, or reproducible offline data snapshot.

## Known limitations retained by the freeze

### Scientific limitations

- Horizontal transforms disable atmospheric refraction, and airmass uses geometric secant
  approximations with feature-specific horizon cutoffs.
- Solar System positions use Astropy’s built-in ephemeris; Moon illumination uses an apparent
  angular-separation approximation.
- Planner, weather, schedule, sampling, and transit-priority outputs use transparent but
  uncalibrated project heuristics.
- Telescope and imaging workflows use idealized optical relations, fixed sampling thresholds,
  approximate target sizes, and simplified mosaics.
- Gaia distance is direct positive-parallax inversion, and absolute magnitude is not corrected for
  extinction or Gaia parallax zero point.
- Exoplanet density, transit probability/depth, temperate screening, and trapezoidal light curves
  are simplified educational calculations.
- Light-curve period/transit outputs are candidates. Sampling aliases, red noise, systematics,
  model selection, and astrophysical confirmation are outside the current models.
- Transit schedules assume a linear ephemeris, constant duration, independent symmetric timing
  uncertainties, finite visibility sampling, and heuristic ranking.

### Architectural limitations

- `app.py` remains a large composition and Observatory UI module.
- Dashboard modules retain pure request/default/formatting helpers behind a Streamlit import.
- Gaia, Exoplanet, and Weather modules combine transport, parsing, domain records, and scientific
  derivation.
- `schedule.py` and `sky_map.py` combine calculations with Plotly presentation.
- Equivalent concepts such as airmass, Moon illumination, visibility, time conversion, and scores
  are implemented in multiple modules without one conventions layer.
- Layering is not enforced, and the package has no supported public API surface.

### Data limitations

- Preset object coordinates and angular sizes are static and are not a complete or maintained
  astronomical catalogue.
- Catalogue queries are row-limited and reflect mutable remote archives.
- Uploaded photometry accepts float times whose unit and reference are not encoded by the values.
- Observation logs and analysis results are held in session memory unless explicitly downloaded.
- No versioned reference dataset, benchmark corpus, or durable data repository is included.

### Provenance limitations

- Scientific products do not consistently record code commit, dependency versions, operating
  environment, input checksum, retrieval time, service/data-release version, transform history,
  units, frame, or time scale.
- Catalogue query text is retained, but the response bytes and archive snapshot are not.
- Exports do not share a common provenance envelope or method-version schema.

### Uncertainty limitations

- Uncertainty is strongest in optional photometric measurements and linear transit ephemerides,
  but is absent from many coordinate, catalogue-derived, equipment, weather, and ranking results.
- Gaia and Exoplanet derived values do not propagate source uncertainties.
- Heuristic scores have no calibrated confidence, error distribution, or sensitivity model.
- Transit timing does not represent covariance, transit-timing variations, or asymmetric and
  non-Gaussian uncertainty.

### Dependency and reproducibility limitations

- Dependency ranges specify minimum versions rather than exact versions.
- CI exercises Python 3.12 only and does not define cross-platform or dependency-matrix
  equivalence.
- Numerical output can drift as Astropy, NumPy, timezone data, or reference data changes.
- There is no machine-readable environment lock, container digest, or archived reference-data
  bundle for v0.2.0.

### External-service and operational limitations

- Gaia, NASA, and Open-Meteo availability, rate limits, latency, and schema changes are outside
  project control.
- There are no recorded-contract snapshots, live health checks, cached fallbacks, or background
  jobs.
- Streamlit session state is ephemeral and string-keyed; no database, autosave, or recovery journal
  exists.
- The repository contains no application authorization, structured observability, deployment
  recovery, hardware driver, safety interlock, or autonomous control layer.

## Reproducibility expectations for future phases

Every experiment, benchmark, scientific comparison, or claim derived from v0.2.0 or later should
record at least:

1. the AstroScope source commit and declared project version;
2. Python, dependency, operating-system, architecture, and timezone-data versions;
3. all input files with cryptographic checksums and complete acquisition metadata;
4. all remote queries, retrieval timestamps, endpoint/data-release identifiers, and response
   snapshots where licensing permits;
5. units, time scales, reference frames, observer location, ephemeris/IERS policy, and conversion
   history;
6. complete algorithm configuration, thresholds, heuristic-policy version, and random seeds if a
   future method is stochastic;
7. raw, intermediate, and final outputs with machine-readable schemas and warnings;
8. the validation dataset, expected result, numerical tolerance, and pass/fail outcome.

Future phases should create a locked experiment environment and versioned reference-data bundle.
Until those exist, reproducing v0.2.0 means recreating the recorded source and dependency state;
installing from the minimum dependency ranges alone is not sufficient evidence of numerical
equivalence.

## Validation expectations for future phases

Software regression and scientific validation must remain distinct:

- Regression tests must preserve explicit v0.2.0 behavior unless a reviewed change intentionally
  replaces it.
- Scientific calculations must be compared with authoritative ephemerides, published datasets,
  calibrated observations, or independent software using documented tolerances.
- Validation datasets must include nominal cases, boundaries, null signals, missing data,
  aliases/gaps, realistic noise and systematics, and known failure cases where relevant.
- Any new scientific output must define units, frames, time scales, provenance, uncertainty, and
  applicability limits before it is used in a claim.
- Heuristics must be labelled as such until calibration data, evaluation metrics, baselines, and
  uncertainty are documented.
- External-service adapters must be validated against versioned contract fixtures; optional live
  checks must not make ordinary offline tests nondeterministic.
- Changes to a v0.2.0 result require an explanation of the algorithm, data, dependency, or
  convention difference and an updated reference result.
- Passing the project test suite is necessary for change acceptance but is never sufficient proof
  of scientific accuracy.

## Blockers carried beyond the freeze

These are not blockers to documenting the Phase 0 baseline; they remain blockers to stronger
research or operational claims:

| Blocker | Prevents | Required future evidence |
|---|---|---|
| No authoritative numerical benchmark suite | Validated scientific-accuracy claims | Reference datasets, independent comparisons, tolerances |
| Incomplete units, time, frame, provenance, and uncertainty contracts | Publication-grade reproducibility | Typed conventions and provenance-aware result schemas |
| Unpinned environment and reference data | Exact long-term numerical reproduction | Lockfile/container and archived data assets |
| Uncalibrated planner/weather/ranking heuristics | Evidence-based observing optimization | Calibration corpus, metrics, baselines, sensitivity and uncertainty |
| Mixed UI/domain/service boundaries | Safe large-scale research extension | Characterization tests and incremental seam extraction |
| Ephemeral state and weak service resilience | Unattended or operational use | Persistence, retries/cache, observability, authorization, recovery |
| No hardware-control safety layer | Robotic observatory operation | Separate control architecture, interlocks, simulation, hazard analysis |

No publication-grade, calibrated-operational, or autonomous claim is part of the v0.2.0 freeze.
